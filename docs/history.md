The request note is content and never goes there.
    - **Backfill** (`backfill_website_ability`): every website's posts row is `live` where it has a post (Stevie's are wired), else `added`; a website with galleries gets a galleries row, `requested` (Stevie's aren't wired).
    - **Admin post summaries** (Rich, 2026-11-02, from the frontend's Accounts aside redesign): `GET /api/admin/accounts` gives each website its posts as `AdminPostSummary { id, postName, status }`, not deleted, drafts included, newest first, so the aside lists each ability's items under it. Names and statuses only, never post content.
    - **Revalidation** gains `{ websiteId, ability }` for On / Off, Remove and Restore; Stevie's route ignores the body.

13. **Request emails** — both, the backend leads. Branch `feat/ability-emails` (backend issue #65). The admin heard of a request message only from the dashboard's "requested" pill. Additive: two new routes, two audit actions, no schema change. Decisions (Rich, 2026-11-02):
    - **One email, to the admin,** each time a site owner sends a request message (the posts request form, or a gallery's message) or edits one (`docs/endpoints.md` → Request Emails). **No "now live" email:** the approval happens outside the Client Portal. Rich wires the content in, replies to the request email with a styling mock-up, the client approves in that thread, and Rich sets it live on the dashboard. Setting it live is his word, not the code's.
    - **Change of mind:** a message already sent can be edited, live or not (`PATCH /api/siteOwner/abilities/:id/request` for posts, `PATCH /api/siteOwner/galleries/:id/request` for a gallery). The edit replaces the note, emails the admin, and puts the ability back to `requested`, so the pill marks it until Rich moves the component and sets it live again. Moving wired-in content is just changing which file imports the component.
    - **Resend,** called only from the backend through its REST API with native `fetch` and no SDK; EmailJS was set aside, being built for sending from the browser. From `notifications@3dwebdev.com` (the domain receives no mail) to every active admin, with **Reply-To the site owner**, so Rich's reply starts the thread with them.
    - **Fire-and-forget after commit,** like revalidation, with a failure reported to Sentry as a warning. The request notes **stay on the admin dashboard** as the record, so a lost email loses nothing and no outbox is needed. This dropped the earlier plan to remove the notes from the admin accounts response.
    - **At most 10 emails per website a day,** counted in memory like the rate limits. A message past the cap is still saved and still flags the dashboard; only its email is skipped.
    - **Production only:** `RESEND_API_KEY` is optional, like `SENTRY_DSN`; empty (staging, local, tests) sends nothing.
    - **Plain text,** with names, the ability, the gallery's name and the note: no ids, no content, no secrets, no link but `https://3dwebdev.com/admin`. Logs and Sentry get the website id only.
    - **Frontend** (its linked issue): an "Edit where it goes" control on the posts message and each gallery's message, prefilled with the current note.
